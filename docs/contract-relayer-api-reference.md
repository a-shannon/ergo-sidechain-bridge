# Contract And Relayer API Reference

This reference is the Gate 8 integration map for external reviewers. It
documents the contract registers, context-extension slots, transaction shapes,
and relayer modules that an integration team must understand before adapting
the bridge.

This is not a production-ready claim. Treat every blocker in
[Institutional Release Checklist](release-checklist.md) as active until linked
evidence replaces it.

## Command Surface

Run these from `relayer/`.

Legacy V1 rehearsal, approval, prebroadcast, and post-submit helpers below are
historical compatibility parsers only. They may inspect immutable evidence for
an exact transaction proven submitted before quarantine; they cannot create or
advance a current execution window. Only unsigned `settle:aggregate prepare*`
diagnostics and exact historical `confirm*`/recovery remain operational. A
future live lifecycle requires a separately versioned external-fee profile and
new profile-specific acceptance tooling.

## Integration Invariants

Do not change these first in an external fork:

- Context-extension Var layout for tracker, DUP, and batch unlock inputs.
- Claim-core byte packing and the 109-byte length.
- Tracker key and value domains, lengths, and byte order.
- DUP key length, marker value, and unified batch insert proof.
- Singleton NFT preservation and output order.
- Require confirmation-time reconciliation before local DUP or tracker state mutation.
- Explicit broadcast opt-in via `BRIDGE_BROADCAST_ENABLED=true`.
- Local WASM signing and node-wallet signing exclusion from production paths.
- ContextExtension guard behavior until upstream conformance evidence exists.
- Gate 4 signer upstream-resolution evidence must bind the same concrete
  signer release identifier in the dependency review `Release action` and
  `Required evidence` cells; a different version, tag, or commit keeps the
  dependency blocker open.
- Trustless candidate evidence remains separate from pre-broadcast approval
  evidence and must not contain `transactionCheck`, `expectedTxId`, `approval`,
  `command`, submit, confirmation, or reconciliation fields. Its
  `trustlessBurnDerivation` must be independently recomputable, and its
  candidate-only `boundary` fields must keep Gate 5 closure, prebroadcast
  evidence, settlement readiness, and production/testnet production-candidate
  claims at `no`.

## Known Limits For Reviewers

- Trustless burn verification is still blocked by the Phase 011 path: sidechain
  commitment, SPV relay, burn inclusion proof, and review evidence.

  throughput claims.
- Aggregate batch settlement caps are contract-level constraints, not operator
  preferences.
- This reference does not replace live devnet/testnet lifecycle rehearsal or
  independent security review.
