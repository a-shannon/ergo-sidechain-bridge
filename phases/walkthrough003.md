## Architecture

### Rebuild-on-Demand Pattern

The bridge AVL+ tree uses the same architecture as production:

1. **No persistent tree state** â€” the WASM crate is stateless
2. **History keys stored in SQLite** (`avl_tree_history` table)
3. **On each operation**: rebuild tree from all historical keys, then generate proofs
4. **Complexity**: O(N log N) rebuild, where N = number of unlock TXs processed

This is acceptable for the PoC because:
- Bridge unlock frequency is low (tens per day, not thousands)
- Rebuild is fast in WASM (< 100ms for 1000 keys)
- Same pattern proven in production production

### Dual Proof Generation

The `DoubleUnlockPrevention.es` contract requires TWO proofs in a single TX:

1. **Lookup proof** (non-membership): proves the TX ID is NOT in the tree
2. **Insert proof**: proves the TX ID WAS inserted

Both proofs must come from the same tree state snapshot. The WASM crate
handles this atomically via `bridge_generate_proofs()`.

## Key Difference from prior art

| Aspect | the reference impl (`reference-avl`) | Bridge (`bridge-avl`) |
|--------|----------------------|----------------------|
| `valueLengthOpt` | `None` (`"00"`) â€” set membership | `Some(1)` (`"0101"`) â€” KV store |
| Value | None (set) | `0x01` (1 byte marker) |
| Purpose | Nullifier tree (has this commitment been withdrawn?) | Unlock prevention (has this TX been processed?) |
| Key size | 32 bytes (commitment hash) | 32 bytes (TX ID) |

## TypeScript Integration

The relayer uses `avl-bridge.ts` as the TypeScript wrapper:

```typescript
import { bridge_generate_proofs, empty_digest } from '../../wasm-avl/pkg/bridge_avl.js';

export function getEmptyDigest(): string {
  return empty_digest();
}

export function insertLockRecord(
  historyKeysHex: string[],
  newTxIdHex: string,
): BridgeProofResult {
  const resultJson = bridge_generate_proofs(
    JSON.stringify(historyKeysHex),
    newTxIdHex,
  );
  return JSON.parse(resultJson);
}
```
