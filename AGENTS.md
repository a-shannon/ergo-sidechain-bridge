# Codex Guide - Ergo Sidechain Bridge

This repository is the active Ergo/Substrate bridge reference implementation.
The canonical execution order and package status live in
`phases/bridge-execution-plan.md`.

## Read First

1. The applicable workspace instructions and Ergo bridge skill.
2. `phases/bridge-execution-plan.md`.
3. The nearest phase plan, protocol document, and tests for the active package.

Do not read `.env` files, secrets, mnemonics, wallet material, private runtime
databases, logs, screenshots, or deployment-state files unless the user
explicitly authorizes that exact critical operation.

## Current Direction

- Gate 5 / Phase 011 is the critical path.
- Substrate/Frontier provides EVM compatibility and commitment production; it
  is not the final trust layer.
- Gate 6 governance work is secondary unless a concrete validator requires it.
- Keep AVL lane work bounded as reference/demo fallback machinery.
- Never claim trustless, production-ready, or mainnet-ready status before the
  complete Gate 5 acceptance closure exists.

## Safety Boundaries

- Observation, construction, JVM check, signing, submission, broadcast
  authorization, transport, and confirmation are distinct capabilities.
- No adapter, local status, `verified` flag, or SQLite row can authorize mint
  or payout.
- Never bypass ContextExtension guards or use node-wallet signing as a
  production workaround.
- Do not push, publish, deploy, broadcast, mutate public GitHub state, or use
  live funds without explicit approval.
- Preserve unrelated dirty or untracked state. Stage only the active package.

## Risk-Proportional Validation

For every material slice, record:

1. the risk profile: `light`, `standard`, `strict`, or `critical`;
2. the work phase: `iteration`, `checkpoint`, `closeout`, or `promotion`;
3. the task-owned paths;
4. the transitive input closure of each deciding check.

Use this cadence:

| Phase | Required validation |
|---|---|
| Iteration | Run only the nearest focused test, parser, compiler, or negative that decides the current edit. |
| Checkpoint | Run the affected producer, consumer, and cross-language checks once for the coherent package. |
| Closeout | Run the complete applicable closure once on the stable package, including independent review for strict/critical protocol work. |
| Promotion | Recheck exact promoted bytes, hashes, configuration, current external state, and publication boundaries. Reuse unchanged closeout results. |

A green result remains reusable while its source inputs, generated bytes,
configuration, authority pins, and deciding external state are unchanged.
Documentation-only edits do not invalidate code, WASM, JVM, node, or release
evidence unless they change the claim or the documented command itself.

Run the full relayer suite only when at least one closed reason applies:

- the user explicitly requests it;
- a coherent fan-out root or shared repository contract changed;
- a focused failure exposes wider impact;
- the package makes a terminal readiness or compatibility claim;
- the package is being promoted or prepared for publication.

Similarly:

- rerun `wasm:test` only when WASM/AVL sources, generated artifacts, locks, or
  their deciding consumers changed;
- rerun a pinned JVM matrix only when its contracts, spec, transaction shape,
  runtime pins, or provenance inputs changed;
- rerun the release gate only when gate logic, evidence, checklist bindings, or
  release claims changed.

Do not rerun a broad gate solely because the phase advanced or a later edit
changed files outside that gate's input closure. Report reused results and the
unchanged closure in the checkpoint summary.

## Critical-Path Throughput

The work package owns the objective, but the default commit batch closes one
independently testable producer-to-consumer join or one fail-closed boundary.
A normal batch changes one to four runtime/source files plus their direct tests;
a work package may span several such batches. Do not create test-only
micro-commits, and do not combine proof, cutover, operations, and release work
into one mega-batch merely because they share a work-package label.

- Keep one main implementation lane on the active critical-path package until
  its coherent Definition of Done is reached.
- Continue through the related mechanical steps inside the selected boundary
  before checkpoint validation; commit when that boundary is independently
  coherent and green.
- Use at most two concurrent subagents. One may own a disjoint implementation
  or deciding research surface; the other may perform independent review or a
  disjoint blocker analysis. Do not keep an agent alive without a concrete
  decision or deliverable.
- Do not duplicate repository exploration, implementation, or test execution
  across agents. The main agent owns shared files, integration, the final diff,
  validation selection, staging, and commits.
- Keep external-blocker monitoring dormant until an upstream pin, activation
  schedule, node capability, or target environment changes. Passage of time is
  not a reason to rerun the same probe.
- Do not add another wrapper, evidence envelope, release validator, or prose
  hardening pass unless the active milestone needs it to connect a producer to
  a deciding consumer or to reject a concrete unsafe path.
- Run broad package closure once after its constituent batches are stable.
  Earlier green batch checks remain reusable while their transitive inputs and
  deciding external state are unchanged.

For each coherent checkpoint, record in the canonical execution plan or active
handoff: the invariant closed, task-owned paths, checks run, reusable green
checks, invalidated checks, residual blockers, and the next executable
milestone. This record is the validation dependency map; a separate tracking
artifact is unnecessary.

## Commit Boundary

Before a local commit:

1. inspect status and the exact diff;
2. run the checks due for the active cadence phase;
3. run `git diff --check`;
4. stage only the coherent package;
5. run `git diff --cached --check`;
6. run the publication guard on staged content;
7. commit only when the package is coherent and green.

Never create a checkpoint commit with known broken tests or misleading claims.
